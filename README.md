# BloodLink — Smart Blood Donation and Donor Matching System

A real, working full-stack application: FastAPI + SQLAlchemy + MySQL backend,
a trained scikit-learn Random Forest for donor prioritization, and a vanilla
HTML/CSS/JS frontend that talks to the live API (no mock data, no
localStorage-as-database).

This has been built and verified end-to-end in development: the backend was
run against a real MySQL instance, the ML model was trained and loaded, the
full pytest suite passes, and the complete workflow (register → login →
create donor/recipient profile → create request → verified hospital → ML
matching → donor accept → fulfillment → donation history) was exercised
live against the running API.

---

## 1. Architecture

```
Frontend (HTML/CSS/JS)
        |  fetch()
        v
FastAPI REST API  (backend/app)
        |
Auth / Business Logic (services/)
        |
SQLAlchemy ORM (models.py)
        |
MySQL Database
```

The matching service calls the ML service (`app/ml/predict.py`) to rank
already-eligible donors. **Blood-group compatibility is never decided by
ML** — it's a fixed, medically verified rules table in
`app/services/compatibility_service.py`.

## 4. Backend setup

```bash
cd backend
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 4.1 Configure the database

Create the database and an application user (adjust credentials as you like):

```sql
CREATE DATABASE bloodlink CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'bloodlink_user'@'localhost' IDENTIFIED BY 'change_me';
GRANT ALL PRIVILEGES ON bloodlink.* TO 'bloodlink_user'@'localhost';
FLUSH PRIVILEGES;
```

(The exact schema is also available standalone in `migrations/schema.sql` if
you prefer to run it directly — FastAPI's startup event will also create any
missing tables automatically against an empty database.)

### 4.2 Environment variables

```bash
cp .env.example .env
```

Edit `.env` and set at minimum: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`,
`DB_PASSWORD`, and a strong random `JWT_SECRET`. See the file for the OTP
and map-provider options — none of them are required to run the app in
development (OTP defaults to logging codes to the console; maps default to
OpenStreetMap, which needs no API key).

### 4.3 Train the ML model

```bash
python -m app.ml.train_model
```

This generates a documented synthetic training dataset (see the module
docstring in `app/ml/generate_training_data.py` for the reasoning and the
SQL to switch to real historical data later), trains a Random Forest, prints
evaluation metrics (accuracy/precision/recall/F1/ROC-AUC + feature
importances), and saves `app/ml/model.pkl` via joblib. If this step is
skipped, matching still works — it falls back to each donor's historical
response rate until a model is trained.

To retrain later with real historical donor-response data:

```bash
python -m app.ml.train_model --csv path/to/real_donor_responses.csv
```

### 4.4 Run the API

```bash
uvicorn app.main:app --reload --port 8000
```

- API root: http://localhost:8000
- Interactive Swagger docs: **http://localhost:8000/docs**
- ReDoc: http://localhost:8000/redoc

The first run creates all tables automatically (via SQLAlchemy's
`create_all` on startup) if they don't already exist.

### 4.5 Create an admin account

Admins **cannot** self-register through the API (the role is rejected). Create
one from the command line:

```bash
python create_admin.py --email you@example.com --name "Your Name" --phone +911234567890
```

(`python seed.py` below also creates a development admin.)

### 4.6 Seed development data (optional but recommended)

```bash
python seed.py
```

Creates 1 admin, 40 donors, 6 recipients, 8 hospitals (7 verified, 1 left
unverified to demonstrate admin verification), and 10 sample historical
blood requests with donor-response history. Credentials are printed at the
end (also see `login.html` in the frontend, which lists them for
convenience). **This is development-only seed data — do not run it against
a production database.**

### 4.7 Run the tests

```bash
pytest -v
```

The suite spins up an isolated SQLite database automatically (see
`tests/conftest.py`) so it never touches your real MySQL database; the
application code itself is MySQL-targeted. The 31 tests cover registration /
login / logout / OTP, admin self-registration being blocked, user
deactivation, hospital verification, request creation + authorization,
compatibility filtering, ranking order, send-to-donor validation, donor
accept/decline, request expiry, status-regression protection, fulfilment and
donation history.

### 4.8 End-to-end check against your real MySQL (recommended)

With the API running and the DB seeded:

```bash
# run the API with its output captured so the OTP step can read the console code
uvicorn app.main:app --port 8000 2>&1 | tee server.log      # terminal 1
python scripts/e2e_check.py --otp-log server.log            # terminal 2
```

It prints 42 pass/fail checks covering the whole workflow.

## 5. Frontend setup

The frontend is plain HTML/CSS/JS — no build step. Serve it as a static
site from its own directory (don't just double-click the HTML files, since
the pages use root-relative paths like `/css/style.css`):

```bash
cd frontend
python -m http.server 5500
```

Then open **http://localhost:5500/index.html**.

The maps use **Leaflet + OpenStreetMap** (no API key needed; loaded from the
unpkg CDN, tiles from tile.openstreetmap.org), so the browser needs internet
access for map tiles. Hospitals, distance-from-me and the hospital preview on
the request form all use real latitude/longitude from MySQL.

**Optional UI test** (needs Node 18+; runs the real pages against your live API):

```bash
cd frontend/tests && npm install && node ui-smoke.mjs   # with API + frontend servers running
```

If your backend runs somewhere other than `http://localhost:8000`, edit
`frontend/js/config.js`.

Make sure the origin you serve the frontend from is listed in the backend's
`CORS_ORIGINS` (`.env`) — `http://localhost:5500` is included by default.

## 6. Using the app

1. Register as a **recipient** or **donor** (you're taken to the OTP step; in
   development the code is printed in the API server console — or click
   *Skip for now*). Or use seeded accounts such as
   `recipient1@bloodlink.dev` / `Recipient@1234`.
2. Donors: **Profile** → blood group, city, latitude/longitude (or "Use my
   current location"). Recipients: **Create Blood Request** → pick a verified
   hospital (map preview), blood group, urgency, units.
3. The **Matching results** page runs: compatibility rules → availability /
   90-day-interval filter → distance → Random Forest ranking. **Nothing is sent
   yet.**
4. Tick the donors you want (or *Select top 3*) and **Send request**. The
   server re-validates every chosen donor, then notifies them.
5. Log in as a notified donor (**Incoming Requests**) and accept/decline.
6. The recipient's **Track Request** page (auto-refreshes) shows the live
   status; after a donor accepts, mark it **Fulfilled**. That updates the
   donor's `total_donations` and writes a `donation_history` row, visible
   under the donor's **Donation History**.
7. Anyone can **Report a problem**; admins triage reports and can
   deactivate users.

**Contact privacy:** when creating a request the seeker gives the patient's
name, a contact person + phone (pre-filled from their account) and optionally
ward/bed. A donor sees **none of this — nor the free-text notes or the
hospital's phone —** until *that donor* accepts; before that they only see
blood group, units, urgency, hospital name/address and distance. After
accepting, the donor gets tap-to-call contact details, and the seeker gets the
accepted donor's phone (still hidden for donors who haven't accepted or who
declined). Donors can only open requests they were actually contacted for.

**Upgrading an existing database** (created before these fields existed):
run `mysql bloodlink < backend/migrations/002_add_request_contact_fields.sql`
once. Fresh installs don't need it.

**Request expiry:** unanswered requests expire automatically — critical 24 h,
high 48 h, medium 72 h, low 7 days (`services/request_lifecycle.py`). Expired
requests refuse matching/responses (HTTP 410).
6. Log in as `admin@bloodlink.dev` / `Admin@1234` to verify new hospitals,
   review users/donors, and manage reports.

## 8. Design notes / important medical logic

- **Compatibility is never ML-inferred.** `compatibility_service.py` is a
  fixed lookup table of standard ABO/Rh donor→recipient rules. The Random
  Forest model only ranks donors *after* this filter, by predicted response
  likelihood — a prioritization signal, never a guarantee, and never a
  factor in whether a donor is medically eligible.
- **Admins can't be self-registered**; only `create_admin.py` / the seed script create them.
- **Status can't regress or be faked.** Users may only set `fulfilled` (after a
  donor accepted) or `closed`; every other status is advanced by the pipeline.
- **Sending is re-validated server-side** — a tampered client can't notify an
  incompatible, unavailable or recently-donated donor.
- **No free-text hospitals.** Blood requests can only be created against a
  hospital row that exists and has `is_verified = true`.
- **Minimum donation interval** of 90 days is enforced in
  `matching_service.py` before a donor is considered eligible again.
- **Real JWT logout**: tokens carry a `jti`; logging out inserts that `jti`
  into a `revoked_tokens` table, checked on every authenticated request —
  so logout has a real, enforced effect despite JWTs being stateless by
  default.
- **OTP-ready architecture**: `otp_service.py` generates, hashes, stores,
  and verifies OTP codes with expiry, defaulting to a console "provider"
  for development. Swapping in Twilio (or another SMS provider) is a matter
  of implementing `_send_via_twilio` and setting `OTP_PROVIDER=twilio` —
  no route or schema changes needed.
